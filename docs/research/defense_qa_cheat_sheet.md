# 学位論文・公聴会想定質問 カンペ

## 1. 研究の立ち位置・新規性

### Q1: 既存ツール（v0等）との違いは？ なぜ自由度を制限（不自由化）した？
*   **UX品質の保証内包**: 自由生成はレイアウトが崩れやすく品質が不安定。Widgetとして「検証済みのUI部品」を利用することで、最低ラインのUXを保証できる。
*   **本質への集中**: UIの「ピクセル調整」ではなく、思考整理の本質である「論理構造（Widget間のつながり）」の生成にLLMのリソースを割くため。
*   **トークン・速度効率**: DOM全体を生成するより、IDと設定値だけを生成するDSLの方が圧倒的に軽量で高速。

### Q2: Level 4（Widget間連動）の必要性は？ ユーザー設定ではダメか？
*   **認知負荷の低減**: 思考中は「ここを変えたらあっちも変える」という作業がノイズになる。自動連動が思考のフローを守る。
*   **文脈依存性**: 「どの項目」を「どう連動させるか」は悩みの内容（文脈）によって変わる。固定的なルールベースでは対応できないため、LLMによる動的生成が必要。
*   **新規性**: 単なるフォーム生成（Level 3まで）は既存にあるが、Widget間の**論理的依存関係**を生成対象にした点が本研究の核心的貢献。

## 2. アーキテクチャ・実装

### Q3: 3段階パイプラインの必然性は？ 1回でできないか？
*   **責務の分離と安定化**:
    *   Stage 1: **戦略**（どの道具を使うか）
    *   Stage 2: **論理**（どうデータをつなぐか）
    *   Stage 3: **詳細**（画面にどう出すか）
*   **エラーの局所化**: いきなり詳細なJSONを書かせると論理破綻しやすい。構造（Stage 2）を固めてから詳細（Stage 3）を埋めることで、手戻りと幻覚を減らせる。
*   **コンテキスト精度の向上**: 各段階で必要な情報のみをプロンプトに与えることで、LLMの注意（Attention）を適切に向けられる。

### Q4: EngineとDSLの責任分界点は？
*   **LLM (DSL)**: 「**何と何を**つなぐか」（依存グラフの定義）を担当。確率的でも良い部分。
*   **Engine (TS)**: 「**どう**値を流すか」（実行と伝播）を担当。決定論的で堅牢な部分。
*   **検疫（Quarantine）**: LLMの出力は「提案」として扱い、TypeScriptの型システムで厳格に検証（検疫）した上で、安全なものだけをEngineに取り込む設計。
*   **循環防止**: LLMには「なるべく循環させるな」と指示しつつ、最終防衛線としてEngineが実行時に循環を検知・遮断する二段構え（これがLayer 1形式健全性100%に寄与）。

## 3. 実験結果・統計・考察

### Q5: 構成B（mini）のログ欠損（n=9）について
*   **事実**: 出力トークン量は正常だったため生成自体は行われたが、保存処理（DB層）でのタイムアウト等が原因と推測される。
*   **対応**: 意図的な選別ではないが、不完全なデータを含めると統計が歪むため、解析からは除外した。$n$数を明記しており透明性は確保している。
*   **傾向**: 残存データでも「形式妥当性（VR）は高いが、時間はかかる」というBの特徴的な傾向は観測できている。

### Q6: 「形式健全性」が100%（天井効果）になった理由は？ 簡単すぎた？
*   **アーキテクチャの勝利**: タスクが簡単なのではなく、**「検疫レイヤ」と「3段階生成」が機能した証拠**。生のLLM出力にはエラーが含まれていたが、システム側で吸収・棄却できた結果。
*   **評価の主眼**: 「100%であること」自体より、**100%にならなかった指標（VR/RC_SR）**にこそモデル間の差と改善余地（ボトルネック）があることを特定できた点が成果。

### Q7: ボトルネック（VRとRC SR）の解釈と対策は？
*   **現状**: DSL構文エラー（VR）と、レンダラが期待する前提条件の不一致（RC_SR）が主な失敗要因。
*   **対策**:
    1.  **正規化（Canonicalization）**: 揺らぎのある出力をルールベースで補正する層の追加。
    2.  **防御的レンダリング**: デフォルト値の拡充や、必須プロパティ欠損時のフォールバック実装。
    3.  **スキーマ制約の強化**: Pydantic等の型定義をより厳密にし、LLMへの制約を強める。

## 4. 応用・限界・UX

### Q8: 生成に30秒（レイテンシ）は実用的か？
*   **現状の認識**: 30秒は対話型アプリとしては許容範囲外。
*   **解決策（実証済み）**: 構成C（Hybrid）やE（Router）では**7秒台**まで短縮できており、モデル選択で解決可能であることを実証した。
*   **今後の展望**:
    *   **ストリーミング**: 生成された部分から順次表示する。
    *   **楽観的UI**: 生成完了を待たずに仮の枠だけ表示する等のUX工夫。

### Q9: generatedValue（初期値）によるバイアスは？
*   **目的**: 「何を書けばいいかわからない（Cold Start Problem）」を防ぎ、思考の呼び水にすること。
*   **対策**: UI上で「AI生成（点線枠など）」と明示し、ユーザーが編集・削除可能にすることで、押し付けにならないよう配慮している。
*   **見解**: バイアスのリスクはあるが、何も書けないまま離脱するリスクの回避を優先した設計。

### Q10: 「意味的な正しさ」の評価は？
*   **今回の範囲**: まずは「システムが動くか（形式的健全性）」と「コスト構造（Layer 2）」の検証にフォーカスした。
*   **今後の計画**: 論文の「Future Work」にも記載の通り、**LLM-as-a-Judge（AIによる判定）と人手評価**を組み合わせた意味的妥当性（Semantic Validity）の評価を行う予定。
    *   例：「生成されたSWOT分析は本当にその悩みに適していたか？」を専門家が採点する等。
